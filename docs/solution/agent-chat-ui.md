# 方案：基础 agent 聊天界面

## 需求要解决的问题

做一个可以发送消息、查看对话的前端聊天界面。这一步完成基础对话和流式输出，不接后端。

后续会接上这些能力，界面结构现在就要能容纳，但这次不实现：

- 工具调用
- MCP 调用
- 上下文窗口，以及上下文压缩
- 人工介入
- 思考过程

约束：界面使用 Element-Plus-X（`vue-element-plus-x`）和 Element Plus。鼠标移入时不做上浮、位移、放大或阴影抬起。

## 候选方案

### 方案 A：基础聊天壳，消息按片段扩展

用 Element-Plus-X 的 `BubbleList` 展示消息，用 `Sender` 发送输入。一条消息由有序片段组成，而不是一整段纯文本。

这一阶段渲染文本片段，并完成流式输出。数据模型同时允许这些片段类型，除文本外先不在界面上画出：

| 片段类型 | 后续对应能力 | 这次 |
| --- | --- | --- |
| `text` | 用户和助手的正文 | 渲染，助手回复按流式追加 |
| `thinking` | 思考过程，以后用 `Thinking` 或 `ThoughtChain` | 不渲染 |
| `tool_call` | 工具调用 | 不渲染 |
| `mcp_call` | MCP 调用 | 不渲染 |
| `human_input` | 人工介入，暂停并等待用户补充 | 不渲染 |
| `context` | 上下文窗口占用和压缩结果 | 不渲染 |

消息状态为 `complete`、`streaming`、`waiting_human`、`error`。发送后先追加一条状态为 `streaming` 的助手消息，后续片段只追加到这条消息的文本上，不新增第二条助手消息。文本全部到达后，状态变为 `complete`。流式期间不能再次发送。

这次没有后端，用本地逐段输出演示流式：助手回复按固定间隔一段段出现在同一个气泡里。接入真实接口时，换成接口返回的数据块，页面追加方式不变。Element-Plus-X 的气泡负责展示已经到达的文本。

页面只有一个聊天视图：上方是消息列表，下方是输入区。没有会话侧栏。

### 方案 B：现在把后续六类能力的区域一起做出来

在基础对话和流式输出之外，同时放上工具时间线、MCP 结果、上下文用量、人工确认条和思考链。这些区域先用假数据填充。

界面一次铺全，但这些能力的契约还没有。工具参数、MCP 资源、压缩策略和人工介入的暂停点都可能在实现时改变，假区域会跟着改。

### 方案 C：只用 Element Plus 自绘聊天

用 `el-scrollbar`、`el-input` 和自定义气泡搭界面，不使用 Element-Plus-X。等后续能力明确后，再换成 `BubbleList`、`Sender`、`Thinking`。

基础阶段组件少，但和现有前端规范不一致。流式输出和思考过程到来时要换掉整套消息渲染。

## 对比

| | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 复杂度 | 低。一个视图、文本片段，加上流式追加 | 高。流式之外还有多块假区域 | 低。但组件是手写的 |
| 改动范围 | `frontend` 的一个聊天视图和消息模型 | 聊天视图加上六块独立区域 | 一套自定义气泡和输入 |
| 风险 | 片段类型如果设得太死，后端字段要对齐一次 | 假界面会在契约确定后返工 | 违反统一使用 Element-Plus-X 的规范 |
| 后续扩展 | 新增一种能力时增加一种片段渲染，不改列表结构 | 区域已经存在，但可能和真实数据对不上 | 要先迁移到组件库，再加能力 |

## 推荐方案

推荐方案 A。

基础界面现在就能用：能输入、能发送，助手回复在同一个气泡里逐段出现，结束后变为完成状态。工具调用、MCP、上下文、人工介入和思考过程仍是消息上的新片段，以后只增加对应渲染，不重做页面骨架，也不改变流式追加方式。正文用 `BubbleList`，输入用 `Sender`，思考过程以后再接入 `Thinking` 或 `ThoughtChain`。

## 不采用其他方案的原因

不采用方案 B。流式输出这次要完成，其余能力还没有接口和交互结论，现在画出来会把未定契约固化进页面。

不采用方案 C。前端规范要求统一使用 Element-Plus-X。自绘聊天会在接入思考过程和流式输出时整块替换。
