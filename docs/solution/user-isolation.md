# 方案：用户隔离

## 需求要解决的问题

后面的会话、巡检记录和 agent 运行都要按人分开。现在前后端都没有用户：前端对话只活在当前页面的内存里，后端还没有应用和接口。任何数据都是全局的，换一个人打开同一份数据就会串。

这一步要引入用户模块，确立两件事：

- 一次请求先变成「当前用户」，再进入后面的业务。
- 一个用户不能读到另一个用户的数据。

用户模块不进入 agent 链路。它不定义 agent，不编排流程，不写提示词，也不做巡检工具。`api/routes` 仍然只做入参校验和调用；用户相关路由调用的是用户模块，不是 workflow。

## 候选方案

### 方案 A：按正常后端做用户模块，会话以后只依赖它

后端做成一个 FastAPI 应用，而不是一段可以随手换掉的内存脚本。用户模块是后面 session 的基础：session 只接收已经解析好的当前用户，不自己读配置、不自己验密码、不自己查用户表。

新增 `backend/app/users/`。这里放用户模型。表和列在模型上声明，创建、读取、更新、删除使用模型基类。用户标识就是用户名。以后的 session 用用户名认出用户，不另建一套数字主键给外部使用。

登录成功后生成一个随机 token，只在响应正文返回一次。Redis 保存 token 的 SHA-256 和用户名，过期时间用 `jwt.expires_minutes`。请求在 `satoken` 头里带上 token。当前用户只从这条 Redis 记录取得，不从请求体里拿。甲带上自己的 token，再在参数里写乙的用户名，也只能读写甲的数据。没有 token、记录不存在、过期或用户已不存在，都返回 401。退出删掉 Redis 记录。成功读取当前用户时刷新过期时间。不使用刷新 token，也不把登录态放进 Cookie。决定过程见 `docs/decisions/001-login-session.md`。

JWT 的签发和解析仍是 `backend/app/users/` 里的单独工具，不放进 agent 的 `tools`。浏览器登录不调用它。`jwt.expires_minutes` 用作上面的会话过期时间。签名密钥写在 `backend/config/dev.yaml`，和数据库配置在同一个文件里。仓库提交 `dev.yaml.example`，值为空。本机的 `dev.yaml` 含密钥，加入 `.gitignore`，不提交。测试不另备配置文件，使用同一台 MySQL 的 `mysql.test_database` 和同一台 Redis 的 `redis.test_database`。

密码写入用户表，不另找地方存。明文不入库。每条密码单独生成盐，加盐后再做单向加密，表里保存盐和加密结果。登录时用同一套盐和算法核对，不能从库里还原出原密码。

应用启动时读取 `backend/config/dev.yaml`。数据库字段为 `mysql.host`、`mysql.port`、`mysql.user`、`mysql.password`、`mysql.database`、`mysql.test_database`。开发和测试共用主机、端口和账号，`database` 是开发库，`test_database` 是测试库。缺文件或缺字段则读取失败。仓库提交 `dev.yaml.example`，值留空。本机文件含密码，加入 `.gitignore`，不提交。

本阶段的接口：

- 发送注册验证码：按用户名生成验证码，并模拟发短信。本阶段不接短信网关，验证码写进日志，接口只返回「已发送」。用户名已注册则拒绝。
- 注册：用户名、密码、验证码。验证码正确后，密码按上面的方式加盐加密，连同用户名写入 MySQL。验证码错误或用户名已存在则拒绝。
- 登录：校验用户名和密码，通过后返回 token，并把哈希写入 Redis。
- 退出：删除 Redis 里的这条会话。
- 读取当前用户：从 `satoken` 头查出用户名，只返回这个用户。未登录返回 401。

隔离用两个用户证明：甲的 token 读不到乙，请求体里写乙的用户名也不行。这个规则放在用户模块里，session 以后沿用同一条入口，不再各写一套。

前端有登录页和注册页。token 放在 `localStorage`，请求带上 `satoken` 头。打开需要登录的页面时，先请求当前用户；没有 token 或接口返回 401，就跳到登录页。登录成功后进入聊天页。退出后回到登录页。聊天页里的消息展示和发送方式不改。

聊天记录要存储，但那是后续工作。这一步不建会话表，也不把现有对话写进 MySQL。session 需求来的时候，它的表带用户名，它的路由通过用户模块拿到当前用户，再按这个用户读写自己的记录。未登录的请求在进 session 之前就被拒绝。

用户模型的测试使用 `test_database`。没有本机配置或测试库连不上时跳过。不另做内存实现，也不另备测试配置文件。

### 方案 B：用户入库的同时把会话也迁到 MySQL

在方案 A 的身份和 MySQL 之上，把现在的前端会话、消息改成后端存储，每条会话都带用户标识，列表和详情都按当前用户过滤。

隔离一次就落到真实对话数据上。代价是用户模块、持久化和聊天协议绑在同一次改动里。聊天现在是本地流式，迁到后端会把流式接口、消息模型和用户模型一起定下来。其中任何一处返工，另外两处都要跟着改。

### 方案 C：只在浏览器里按本地用户分开

前端用本地存储保存多个用户和各自的会话，切换用户就切换本地数据。后端仍然没有用户。

浏览器里能分开，但身份由页面自己声明。服务端无法拒绝「我是另一个人」。后面接口一旦出现，这层隔离就不起作用。

## 对比

| | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 复杂度 | 中。一个模块、三个接口、MySQL 和一份 YAML 配置 | 高。还要定会话接口和流式协议 | 低，但只在浏览器内 |
| 改动范围 | `backend/app/users/`、用户路由、MySQL、Redis 与 YAML、登录页和未登录跳转 | 再加会话表、聊天接口和现有对话区 | 只改前端 |
| 风险 | 本机要有 MySQL 和 Redis；密码文件一旦提交就会泄露 | 用户和聊天耦合，任一块返工都会扩大 | 不能作为服务端隔离 |
| 后续扩展 | session 只消费当前用户，自己的表以后再加 | 对话已经按用户隔离，但方案被聊天协议绑住 | 接入后端时要推倒重来 |

## 推荐方案

推荐方案 A。

用户隔离的变化点是「请求如何变成当前用户」和「数据如何只属于这个用户」。这两件事做成正常的后端能力：FastAPI 应用、MySQL、Redis、YAML 配置、注册（含模拟短信）、登录、退出。用户标识是用户名，只从 Redis 里的登录会话取得。前端没有登录就进入登录页。聊天记录的存储留到后续 session 需求。

## 不采用其他方案的原因

不采用方案 B。会话持久化和流式协议是下一项需求。把它们和用户模块绑在一起，会在用户边界还没定稳时改动已经可用的聊天界面。

不采用方案 C。本地切换不能阻止伪造身份，不满足用户隔离。
